# AGENTS.md — Smart Campus (UAJS)

## Sesión y tokens

- **Vigencias**: el access token dura **15 minutos** (`JWT_EXPIRES_IN=15m`), valor por defecto en los 6 servicios de `backend/docker-compose.yml` y en `backend/.env.example`. El refresh token dura **7 días** (`JWT_REFRESH_EXPIRES_IN=7d`). Los fallbacks en el código son `15m` y `7d` (`backend/services/users-service/src/controllers/authController.js`).
- **Estado de sesión en el frontend**: el token, el refresh token, el usuario y el rol se guardan en `localStorage` con las claves `smart-campus-token`, `smart-campus-refresh`, `smart-campus-user` y `smart-campus-role`. Toda la lectura y escritura está centralizada en `frontend/src/services/authService.js`.
- **Renovación automática ante 401**: en `frontend/src/services/api.js`, un 401 que **no** sea de `/api/auth/login` ni de `/api/auth/refresh` dispara **un único** intento de refresh (varias peticiones con 401 simultáneo comparten una sola llamada `POST /api/auth/refresh`). Si el refresh funciona, se guarda el nuevo access token, se actualizan usuario y rol con el `usuario` devuelto por el backend y se reintenta la petición original **una sola vez**. Si el refresh falla o no hay refresh token, se limpia toda la sesión (token, refresh, usuario y rol) y se redirige a `/login`. Un 401 en `/api/auth/login` no redirige ni recarga la página: lanza el error "Credenciales inválidas" (o el mensaje del backend) para que lo muestre el formulario de login.
- **El refresh token no rota ni se revoca**: el backend no emite un refresh token nuevo ni mantiene lista de revocación. La **única** revocación efectiva es desactivar el usuario en la BD (`users.activo = 0`); en ese caso el refresh responde 401 y el frontend limpia la sesión y vuelve a `/login`.

Deben preservar las variables ajenas al cambio, no reproducir secretos en respuestas, logs ni diffs, y nunca incluir ese archivo en commits.
